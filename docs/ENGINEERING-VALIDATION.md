# 엔지니어링 검증

## 책임과 현재 적용 범위

측정·검증 방법의 기준이며 실험 결과 보고서가 아니다. 제품 목표·합격 기준·실제 결과의 위치는 [AGENTS](../AGENTS.md#작업-목적에-따라-읽을-문서)를 따른다.

현재 구현·측정 도구·자동화 구성은 없다. 아래는 검증을 설계하는 틀이며 기술 도구·실험 규모·합격 목표값은 미정이다. 실제 존재하지 않는 테스트·부하 명령을 적지 않는다.

## 최소 측정 항목

| 영역 | 최소 기록 지표 | 기준선·판정 조건 |
| --- | --- | --- |
| 대전 완료 | 시도 수·완료 수·중단 사유, 턴/라운드 진행 | 작업의 수용 기준과 대조. 대상 수·목표율 미정 |
| 입력·상태 동기화 | 명령부터 사용자 화면 반영까지 지연, 실패·중복·불일치 수 | 동일 네트워크·동일 시나리오의 첫 측정을 기준선으로 보관. 목표값 미정 |
| 클라이언트 | 프레임 시간·평균/하위 구간 fps, 멈춤·오류 | PRD의 약 60fps 목표와 대조. 기기·브라우저·구간·판정식은 [fps 측정 절차](#fps-측정-절차-val-001) |
| 서비스 부하 | 동시 접속·동시 대전 수, 요청 지연·오류율, CPU·메모리, 이벤트 루프·틱 지연(`tick_skipped`), 스냅샷 전송 지연, 서버 송신 대역폭 | 단일 대전 기준선부터 증가. 변수는 동시 방 수(1·3·5)와 알 이동 중 스냅샷 주기(초당 10·20·30회)이며 한 번에 하나씩 바꾼다([OPERATIONS](design/OPERATIONS.md#사용량부하-확인)). 유지 시간·중단 임계값 미정 |
| 실패·복구 | 장애 지점·재현 횟수·복구 시간·유실·중복 저장 수 | PRD의 보관 정책과 대조. 서버 장애 처리는 MVP에서 고려하지 않으므로 실험 대상에서 제외 |
| 비공개 정보·권한 | 노출·비허용 명령 수, 거부 응답과 상태 변화 | 방해요소·게임 요구사항과 대조. 관찰 방법은 설계에 맞춰 선택 |
| 비용 | 사용량·한도·관찰 기간·실제 청구 | PRD의 0원 목표와 대조. 서비스 선정 후 포함 비용 정의 |

## 기준선·부하 실험 절차

1. 작업 ID와 PRD·설계·DEC ID를 지정하고 가설·관찰 결과·판정 조건을 적는다. 미정인 목표값은 실험 전에 임의 확정하지 않는다.
2. 커밋·작업 파일 변경 여부·기기·OS·브라우저·네트워크·실행 구성·데이터·시드를 기록한다.
3. 단일 대전 또는 해당 기능의 최소 시나리오로 기준선을 측정한다. 준비·워밍업·측정 구간·반복 횟수를 구분한다.
4. 같은 조건에서 한 변수씩 바꾼다. 부하 단계·유지 시간·중단 조건은 사전에 기록한다.
5. 평균뿐 아니라 분포·표본 수·오류·편차를 남긴다. 같은 조건으로 전후를 비교하지 못하면 한계로 적는다.
6. 결과와 원자료 위치를 worklog에 남기고 TASKS의 수용 기준과 연결한다. 목표 미정이면 관찰 결과만 기록하고 합격으로 표시하지 않는다.

## fps 측정 절차 (VAL-001)

목표는 [PRD 비기능 요구사항](PRD.md#4-비기능-요구사항과-제약)의 "평균 60fps에 가깝게, 하위 5% 구간 30fps 이상"이다. 이 절은 그 목표를 재는 방법이며 측정 결과는 worklog에 남긴다.

| 항목 | 정함 |
| --- | --- |
| 환경 | 개발자 노트북, 최신 Chrome, 창 크기 1280×720. 기기 모델·OS·Chrome 버전·전원 연결 여부·다른 탭 수를 기록한다 |
| 측정 구간 | 게임 화면에 진입한 때부터 결과 화면이 뜨기 직전까지, 한 판 전체. 로비·대기실·결과 화면은 제외한다 |
| 도구 | 구현 전에는 측정할 수 없다. 구현 후 **Chrome DevTools의 Performance 패널**(프레임 기록)과 FPS meter로 관찰하고, 판 전체의 프레임 시간 원자료가 필요하면 개발용 프레임 시간 기록 코드를 구현 작업에 등록한다. 존재하지 않는 도구·명령을 미리 적지 않는다 |
| 원자료 | 프레임 간격(ms) 목록. 이를 요약한 값(프레임 수, 측정 시간, 평균 fps, 프레임 시간 95백분위)을 기록하고, 원자료 파일 위치를 worklog에 연결한다 |
| 반복 | 같은 조건으로 3판 이상. 판마다 따로 기록하고 평균만 남기지 않는다 |
| 장면 | 한 판에서 알이 많이 움직이는 구간(충돌·알 떨어짐)과 방해요소 효과(시야 방해 등)가 켜진 구간을 구분해 관찰한다. 구간 표시는 시각(판 시작 후 초)으로 남긴다 |

판정식(판마다 계산):

- 평균 fps = 프레임 수 ÷ 측정 시간(초).
- 하위 5% fps = 1000 ÷ 프레임 시간 95백분위(ms). 이 값이 **30 이상**(프레임 시간 95백분위 33.3ms 이하)이면 하위 5% 기준을 충족한다.
- 평균 fps가 **55 이상**이면 "60fps에 가깝게" 기준을 충족한다([DEC-034](DECISIONS.md#결정-색인)). 판마다 계산하고, 3판 모두 충족해야 한다.
- 멈춤(프레임 간격 100ms 이상) 횟수와 시각을 함께 기록한다.

## 플레이 테스트 기록 양식 (VAL-001)

[PRD 성공 기준](PRD.md#5-성공-기준) 5개를 판정하는 기록 양식이다. 실제 기록은 플레이 테스트 날짜의 worklog에 이 양식의 표를 복사해 쓴다. 참가자는 실명 대신 `P1`처럼 번호로 적는다.

공통 항목: 날짜, 빌드 커밋, 참가자 번호, 각자의 기기·브라우저, 네트워크(같은 망 여부), 판 번호, 방 종류(PvP·로컬), 알 개수·라운드 설정.

| 성공 기준 | 기록 항목 | 판정식 |
| --- | --- | --- |
| 1. 서로 다른 PC의 두 사용자가 한 판을 끝까지 플레이 | 판마다: 시작 시각, 종료 방식(정상 종료·기권·시간초과 3회 기권·오류 중단), 중단 원인, 오류 메시지. 참가자별 완료한 판 수 | 참가자 4명 이상, 각 3판 이상이면서 **(시작한 판 − 오류 중단 판) ÷ 시작한 판 ≥ 90%**. 정상 종료·기권·시간초과 기권은 규칙에 따른 종료라 모두 완료로 세고, 오류로 멈춘 판만 중단으로 센다 |
| 2. 방해요소를 언제 어떻게 쓸지 고민하게 된다 | 플레이 후 질문 "방해요소를 언제 왜 썼나요": 응답자별 사용 시점과 이유 원문, 쓰지 않고 끝난 방해요소 수, 방해요소 종류별 사용 횟수 | 사용 시점과 이유를 **둘 다 설명한 응답자 ÷ 응답자 > 50%**. 한쪽만 말하면 설명한 것으로 세지 않는다 |
| 3. 한 판 후 다시 하고 싶어진다 | 응답자별 재대전 의향(예·아니오·모름), 판마다 결과 화면에서 재도전하기가 성립했는지 | 재대전 의향 "예" 응답자 ÷ 응답자 > 50% **또는** 재도전하기 성립 판 ÷ 끝난 판 > 50% (PRD의 "또는"을 따름). 둘 다 기록한다 |
| 4. 회원 정보와 전적이 서버 재시작 후에도 유지 | 경기 전·경기 후·서버 재시작 후 각 시점의 회원 목록(닉네임)과 계정별 판수·승·패·무, 재시작 방법·시각 | 세 시점의 모든 계정 값이 경기 반영분만 늘고 재시작 전후로 **완전히 일치**하면 충족. 하나라도 다르면 불충족하고 차이를 적는다 |
| 5. 월 비용 0원으로 운영 | 배포일, 서비스별(Render·Neon·헬스체크 서비스·도메인) 사용량·한도·청구서 항목, 확인 날짜 | 배포 후 1개월 동안 **모든 서비스의 실제 청구 합계 = 0원**. 배포 후 1개월이 지나기 전에는 "관찰 중"으로 적고 합격으로 표시하지 않는다 |

보조 기록(밸런스 조정용, 합격 판정에는 쓰지 않는다): 선공 승률, 방해요소별 사용 횟수, 체감 불공정 응답, 바꿀 수치와 관찰 결과([수치 변경 절차](design/GAME.md#수치-변경-절차)).

## 실패 실험 절차

- 실험 환경·복구 수단·관찰 지표를 정하고 연결 종료·프로세스 재시작·중복 요청·저장 실패 중 재현할 실패를 선택한다.
- 정상 기준선을 확인하고 정한 단계에서 실패를 주입한 뒤 사용자 안내·턴·결과 저장·복구를 관찰한다.
- 같은 조건에서 재현하고 원상 복구를 확인한다. 승인 정책과 관찰이 다르면 차이와 미결 사항을 기록한다.
- 원인·해결·회귀 검증이 재사용 가능한 문제는 [TROUBLESHOOTING](TROUBLESHOOTING.md)에 사례를 등록한다.

## 기능·회귀 검증 설계 후보

- 물리·승패·턴·시간·방해요소 효과의 단위 검증, 시간·난수 통제 시 결정성 검증
- 사용자별 뷰의 상대 보유 방해요소·시야 방해 정보 노출 검사
- 비허용 방해요소·남의 턴 발사·판 밖 대상 등 입력 경계 검사
- 서로 다른 PC·지원 브라우저에서 방 입장부터 경기 결과 확인까지 검사

도구(Vitest 등)와 테스트 계층·자동화 범위는 미정이다.

## 문서 변경 검증

- 이동 후 상대 링크·앵커·문서 경로와 문서별 책임의 일관성을 확인한다.
- 원문의 요구사항·미정 표시·방해요소 목록이 누락되거나 임의 확정되지 않았는지 대조한다.
- 작업 상태·제품 정책·설계·결정 근거가 서로 다른 파일에서 중복 기준으로 관리되지 않는지 확인한다.
- 검사 도구·명령·검사 범위·결과·제외 범위를 worklog에 기록한다.

## 실험 기록 양식

[worklog 양식](worklogs/TEMPLATE.md)을 사용한다. 작업/실험 ID, 가설, 기준선, 변수, 환경·리비전, 데이터·반복·시간, 실제 명령, 관찰값·원자료, 판정, 한계·재현성, 문서 대조와 후속 작업을 남긴다.
