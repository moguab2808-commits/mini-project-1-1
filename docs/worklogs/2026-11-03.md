### 수행과 관찰

1. 시작 준비가 5초보다 늦으면 `GameService.#waitStarted`가 먼저 풀려 경기 없는 이탈을 처리하고 이후 시작이 다시 진행될 수 있었다. 시작 준비 훅을 서비스 안의 동일한 완료 신호에 포함하고 임의의 5초 우회를 없앴다. 단위 테스트에서 시작을 6초 지연해 이탈이 기다리는지, 시작 실패도 대기를 해제하고 전적을 만들지 않는지 확인했다.
2. 두 사용자의 이탈 훅·DB 변경이 동시에 돌면 참여자 정리와 방장 정리가 같은 세션을 건드린다. 시간 제한 제거 뒤 실제 클라이언트 통합 테스트 정리에서 방이 남는 것으로 재현했다. 방별 이탈 직렬화와 잠금 안 재조회로 해결했다. 두 좌석 동시 `leave()`가 완료되고 전적이 각각 한 번 저장되는 통합 테스트를 추가했다.
3. 이탈 종료의 `rematchDeadlineMs`가 API 표와 달리 채워졌다. 런타임이 수락한 이탈 기권에는 `null`, 방에 남아 기권 버튼만 누른 경우에는 기존 재도전 마감을 전달한다. 이벤트와 최종 뷰가 같은 결과를 가진다. 이는 새로운 제품 정책이 아닌 기존 API 계약과의 정합성 수정이다.
4. 기존 런타임이 `game:over`를 보낸 뒤 최종 `game:state`를 보냈다. 최종 신뢰 전송 뷰를 결과 이벤트보다 먼저 보내 API 순서 규칙 6에 맞췄다. `game-service.test.ts`에서 종료 뒤 상태 이벤트가 없음을 확인했다.
5. PR #63의 `INTERNAL_ERROR` 추가를 원격 명령 ack에 그대로 수용했다. PR #62는 이미 병합됐으므로 IMPL-005 완료 상태도 맞췄다.

## IMPL-010 온라인 대전 클라이언트

### 범위와 기준 문서

[IMPL-010](../TASKS.md#impl-010-온라인-대전-클라이언트), [LOCAL GameSession](../design/LOCAL.md#gamesession-시그니처)·[온라인 연결 구성](../design/LOCAL.md#온라인-연결-구성), [API 이벤트 순서](../design/API.md#이벤트-순서), DEC-030.

### 구현

- `RemoteGameSession`: 기존 GameSession 구현. 발사·방해요소·기권·재도전·판 돌리기의 ack 객체를 그대로 전달하고, 조준·몸짓 입력은 volatile로 보낸다. 다른 경기·지나간 시작·증가하지 않은 revision·종료 뒤 이벤트를 버린다.
- `RoomClient`: 방 생성·참가·즉시 참가·이탈, 방 상태·폐쇄, 중복 접속·연결 실패·끊김을 처리한다. `room:state` 처리 중 동기적으로 세션과 스토어를 생성해 시작·지급을 놓치지 않는다. 재도전과 방장 대기 뒤 새 참여자도 같은 세션을 사용한다.
- `SocketRequests`: 명령 ack에 임의 시간 제한을 두지 않고 연결 종료·정리 때 대기를 마친다. 자동 재접속을 끄고 로그인 전환 콜백을 한 번만 호출한다. 소켓 이벤트 구독과 스토어를 정리한다. 원격 `dispose()`는 `room:leave`를 보낸다.
- `/online`: 기존 `GameScreen` 코드를 바꾸지 않고 원격 세션을 넘기는 개발용 연결 확인 화면. 같은 출처 인증 쿠키가 필요하며 정식 로그인·로비 화면은 IMPL-012다. 연결 종료는 `/login` 이동에 연결했다. Vite 개발 서버는 `/api`·`/socket.io`를 기본 서버 포트로 프록시한다.
- `online.test.ts` 9건: ack 이전 시작·지급, 재도전·다음 참여자, 낡은 이벤트·뷰, 모든 오류 코드의 객체 동일성, 닫힌 방의 늦은 성공 ack, 시작 실패, 세 종류의 접속 종료, dispose 정리.
- `tests/integration/online.db.test.ts` 5건: 실제 인증·Socket.IO·DB로 두 계정 입장→발사·몸짓→기권 종료→재도전→참여자 이탈→다음 참여자, 동시 이탈, 중복 접속, 서버 연결 종료, 시작 실패를 검증한다. 테스트 설정은 외부에서 지정한 DB URL도 받으며 저장소 밖 통합 테스트를 포함한다.

## PR #64 리뷰 반영: 시작 중단 신호·API 표 이스케이프

### 범위와 기준 문서

- PR #64 리뷰 2건. ① `RoomService.#startOnJoin`의 사용자 조회(`findUserById`)가 DB 오류로 던지면 `try` 밖이라 입장 되돌리기도 `onStarted`도 실행되지 않아, 방이 `playing`·`guest_id` 채움으로 남고 `session.started`가 풀리지 않는다. 이후 방장 이탈의 `#onLeave`가 방 잠금을 쥔 채 영원히 기다린다. ② [API](../design/API.md) 표 두 행의 `\|`가 `\ |`로 바뀌어 열이 갈라졌다.
- 기준: [DEC-043](../DECISIONS.md#결정-색인) ②, [DATABASE 방 생명주기](../design/DATABASE.md#방-생명주기), [API 이벤트 순서](../design/API.md#이벤트-순서).

### 수행

- `#startOnJoin` 전체를 `try`로 감쌌다. `onStarted`에 닿기 전에 실패하면(사용자 조회 실패, 사용자 행 없음, `room:state` 전송 실패) 새 훅 `RoomHooks.onStartAborted`를 부른 뒤 `#undoJoin`으로 입장을 되돌리고 원래 오류를 올린다. `onStarted` 실패는 기존대로 `#undoJoin`만 한다. 사용자 행이 없을 때 조용히 반환하던 경로도 같은 실패로 바꿨다.
- `GameService.#onStartAborted`: `#onStarted` 실패 경로와 같게 세션을 버리고 `session.started`를 푼다. 이탈이 먼저 만든 세션의 신호를 풀도록 `#sessionOf`로 같은 세션을 찾는다. `app.ts`에서 연결했다.
- DEC-043 ②의 적용 범위를 "`onStarted` 실패"에서 "시작 커밋 뒤 시작 처리 실패"로 넓혀 DATABASE·API 문서에 반영했다. 정책(입장 되돌리기·`INTERNAL_ERROR`)은 그대로다.
- API 표 두 행(`room:closed`, `game:over`)의 `\ |` 3곳을 `\|`로 되돌렸다. `docs/`는 Prettier 대상이 아니므로(`config/prettier.ignore`) 저장소 포맷터가 아닌 편집 도구의 부작용으로 보인다.

### 검증 조건·결과

### 작업·검증 조건

- 브랜치 `feat/val-002-frame-recording`(기준 `main` 18f1233), 미커밋 상태에서 확인.
- WSL2 Linux, Intel i5-1335U(12스레드), Node 24.22.0. 브라우저는 Playwright 1.64.1(npx 캐시)의 Chrome for Testing 156.0.8078.4 headless shell, 창 1280×720, WebGL은 SwiftShader(CPU 렌더링). 실행에 필요한 `libasound.so.2`가 없어 `libasound2t64` deb를 시스템에 설치하지 않고 스크래치 디렉터리에 풀어 `LD_LIBRARY_PATH`로만 썼다.
- 개발 서버 `vite`(포트 5199), 한 브라우저 컨텍스트에 `/local?seat=0`·`/local?seat=1` 두 창. 경기 시작 2초 뒤 seat 0을 앞으로 가져오고 8초 기다린 뒤 seat 1 창을 닫아 seat 0에 기권 결과를 띄웠다. 입력(발사·방해요소)은 하지 않았다. 3회 반복.

### 수행과 관찰

1. 운영 빌드: `npm run build -w @alkkagi/client` 후 `dist/`에서 `frame-recorder`·`FrameRecorder`·`alkkagiFrame`·`하위5%`를 grep해 일치 없음. 수용 기준 1 충족.
2. 브라우저(수정 전): 결과 전에는 `window.__alkkagiFrameReport`가 없고, 결과 화면("승리! 기권으로 끝났어요")이 뜨면 콘솔에 `[frame-recorder]` 요약이 찍히며 보고서가 생긴다. 결과 뒤 1.5초 동안 프레임 수가 그대로였다. `window.__alkkagiDownloadFrameReport()`로 `frame-report-local-1.json`을 내려받았고 파일의 프레임 수가 보고서와 같았다.
3. 의심과 정정: seat 1을 닫은 뒤 보고서가 3~5초 늦게 보였다. 별도 rAF 카운터로 보니 창을 닫는 동안 seat 0의 rAF가 약 3초 멈췄지만, 결과는 닫은 직후(약 50ms) 도착해 기록이 이미 끝난 뒤였다. 멈춤은 측정 구간 밖(결과 뒤)이고 Playwright의 `evaluate`가 늦게 돌아온 것이다.
4. 보정: 기존 `stop()`은 마지막 프레임 시각에서 측정을 끝내므로, 결과 직전에 화면이 멈춰 다음 프레임 전에 결과가 오면 그 멈춤이 원자료·측정 시간·멈춤 횟수에서 빠진다. `stop(nowMs?)`가 마지막 프레임부터 `nowMs`까지를 마지막 간격으로 닫게 하고, 화면은 `stop(performance.now())`를 부른다. 단위 테스트 1건 추가(2초 멈춤이 간격·측정 시간·멈춤으로 남고, 같거나 이전 시각이면 간격을 더하지 않음).
5. 보정 후 3회: 프레임 48·36·37, 측정 시간 10.96·11.07·11.09초, 평균 4.4·3.3·3.3fps, 100ms 이상 멈춤 33·23·23회, 결과 뒤 프레임 불변·내려받기 정상. 진단 실행에서 마지막 간격(마지막 프레임→결과) 84ms가 원자료에 들어갔다. 수용 기준 2 충족.
6. `npm test` 26개 파일·304개(기존 303 + 1), `npm run lint`, `npm run format`, `npm run build` 통과.

### 한계·미검증

- 위 fps 값은 SwiftShader CPU 렌더링에서 두 창이 같은 렌더러를 나눠 쓴 값이라 성능 판정에 쓰지 않는다. 실제 GPU·Chrome에서 3판 측정은 플레이 테스트 때 [fps 측정 절차](../ENGINEERING-VALIDATION.md#fps-측정-절차-val-001)대로 한다.
- 정상 종료(알 모두 떨어짐)·`/ai`·`/online` 결과로 끝나는 판은 브라우저로 돌리지 않았다. 세 화면 모두 같은 `GameScreen`의 `state.result`로 기록을 끝내므로 종료 방식과 무관하다고 보지만 직접 확인하지는 않았다.
- `mark`(장면 구간 표시)는 화면에 연결하지 않았다. 수용 기준 밖이며 측정 절차에 장면 시각을 직접 적도록 했다.
- 원자료 JSON은 검증용 스크래치 파일이라 저장소에 넣지 않았다.
