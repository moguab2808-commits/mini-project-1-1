## 기존 후보: 로컬·온라인 모드 경계

로컬에서 먼저 게임을 완성하고 온라인으로 넘어가는 순서를 위해, **UI가 "게임을 진행하는 방법"을 인터페이스 뒤에 숨긴다.**

```
        ┌──────────── UI (R3F 장면, 정보 패널, 증강 영역) ────────────┐
        │          GameSession 인터페이스에만 의존                    │
        └───────────────┬──────────────────────┬───────────────────┘
                        │                      │
              LocalGameSession          RemoteGameSession
              (M1: 브라우저 안에서       (M2: Socket.IO로
               game-core 직접 호출)       서버와 통신)
                        │                      │
                        └──── game-core ───────┘  ← 서버도 같은 코드를 호출
```

- **`GameSession` 인터페이스(안)**: 명령(`pickAugment`, `submitShot`, `forfeit`)을 보내고, 이벤트(`augmentChoices`, `turnChanged`, `simulationResult`, `gameOver`)를 구독한다. 이벤트 모양은 [API 후보](API.md)와 **같은 타입**을 쓴다. M2에서는 `LocalGameSession`을 `RemoteGameSession`으로 바꾸는 것이 전환의 전부가 되도록 한다.
- **M1 로컬 모드**: 한 PC에서 두 플레이어가 번갈아 플레이한다 (개발용 `/local` 경로). 서버, DB, 로그인이 필요 없다.
- **로컬 모드의 비공개 정보 문제**: 한 화면을 같이 보면 분신이 상대에게 노출된다. 로컬 테스트에서는 (a) 턴이 넘어갈 때 "화면 가리기 / 교대" 화면을 두거나, (b) 개발용 토글로 분신 구분 표시를 켜고 끄는 방식을 쓴다 (아래 미정 항목).
- **게임 상태 머신**은 `game-core`에 둔다: 증강선택 → 턴 → 시뮬레이션 → 판정 → 종료. 타이머(30초 / 20초)는 `game-core`가 시계를 직접 읽지 않고 **외부에서 시간을 주입**받는다 (로컬은 브라우저 타이머, 서버는 서버 타이머).

## 미정 사항

- 코드 디렉터리·패키지 위치·의존 방향·모노레포와 빌드 구성
- UI와 게임 세션의 경계, 로컬·원격 구현 교체 방식
- 한 PC에서 분신·안개를 검증할 화면 교대·시점 토글 방식
- 로컬 DB·인증 대체 가능 범위와 배포 구성과의 차이
- 개발용 설정·환경변수 이름과 안전한 예제 관리: [운영 설계](OPERATIONS.md)

실제 설치 명령과 접속 주소는 구성 후 README에 추가하고 검증 결과는 worklog에 기록한다.
