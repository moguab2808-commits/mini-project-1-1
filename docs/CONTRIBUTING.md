# 두 개발자의 협업 규칙

## 기본 흐름

Issue 선택·담당 확정 → 관련 문서 확인 → 필요한 계약 합의 → 작업 브랜치에서 구현·검증 → PR → 상대방 리뷰 → 기준 브랜치에 병합 → Issue 종료.

- 담당은 Issue에서 두 사람이 확인한다. 작업별 문서는 [AGENTS.md의 읽기 순서](../AGENTS.md)에 따라 확인한다.
- 기준 브랜치는 [구현 현황](PROGRESS.md)에 명시한다. 작업 브랜치는 기준 브랜치에서 분기하고 PR의 병합 대상도 확인한다.
- [PR 양식](../.github/pull_request_template.md)에 변경·검증·문서 갱신을 기록한다. 상대방은 Issue 완료 조건, 합의한 명세, 검증 결과를 확인한다. 리뷰에서 나온 피드백을 반영하고 병합한다.
- 기준 브랜치의 구현 현황·막힌 문제·다음 방향이 바뀌는 PR에는 `PROGRESS.md` 갱신안도 함께 담는다. 갱신안은 해당 PR이 병합된 뒤의 기준 브랜치를 기준으로 서술하며, 병합 전 작업은 완료로 집계하지 않는다. 완료 조건을 충족한 변경이 병합되면 Issue를 종료한다.

## 작업 상태

상태는 해당 GitHub Issue 본문에 아래 네 상태 중 하나로 표시하고 갱신한다. 별도 상태표나 저장소 설정 변경은 필요하지 않다.

| 상태 | 기준 |
| --- | --- |
| 예정 | 아직 착수하지 않은 작업 |
| 진행 중 | 담당 확정 후 합의·구현·검증 중인 작업 |
| 리뷰 중 | PR을 열어 상대방 검토를 받는 작업 |
| 완료 | 완료 조건을 충족한 변경이 기준 브랜치에 병합된 작업 |

## 연동 계약과 기록

- 연동 기능은 구현 전에 요청·응답·오류 형식과 필요한 검증 규칙을 관련 담당자끼리 합의하고 [DESIGN.md](DESIGN.md)에 기록한다. 계약 변경도 관련 담당자와 합의 후 명세와 코드를 같은 PR에서 수정한다.
- 간단한 결정은 [DECISIONS.md](DECISIONS.md), 중요한 결정은 ADR로 남긴다. 공유할 결정과 검증 결과를 로컬 메모에만 남기지 않고 해당 문서와 Issue·PR에서 연결한다.
- 복잡한 작업에만 개별 작업 문서를 추가한다. 운영 문서와 트러블슈팅 기록도 실제 필요가 생겼을 때 추가하며 기존 기준 문서와 중복 작성하지 않는다.
