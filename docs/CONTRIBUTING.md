# 두 개발자의 협업 규칙

## 기본 흐름

TASKS의 작업 선택·담당 조율 → 관련 기준 문서 확인 → 필요한 요구사항·계약 합의 → 작업 브랜치에서 수정·검증 → worklog 기록 → PR → 상대방 리뷰 → 기준 브랜치 병합 → TASKS 완료 반영.

- 작업 ID·우선순위·의존성·상태·수용 기준은 [TASKS](TASKS.md) 한 곳에서 관리한다. Issue는 토론과 담당 조율에 사용하고 TASKS의 해당 작업을 연결한다.
- 작업별 문서 선택은 [AGENTS](../AGENTS.md)를 따른다. 작업 중 다른 사람의 변경을 덮어쓰지 않는다.
- 기준 브랜치는 [PROGRESS](PROGRESS.md)에 명시한다. 작업 브랜치와 PR 병합 대상을 확인한다.
- [PR 양식](templates/PULL_REQUEST.md)에 작업 ID, 변경 내용, worklog의 검증 근거, 기준 문서 갱신을 연결한다. 리뷰는 TASKS 수용 기준·설계·검증 근거를 기준으로 한다.
- 수용 기준이 충족돼도 리뷰·기준 브랜치 병합 전에는 작업을 완료로 표시하지 않는다. PR에 병합 후 반영할 현황 갱신안을 포함할 때는 병합 전 작업과 기준 브랜치 상태를 구분한다.
- 이슈의 작업을 마무리하는 PR(수용 기준을 모두 체크한 PR)은 본문에 `Closes #이슈번호`를 적어 병합 시 이슈가 자동으로 닫히게 한다. 마무리하지 않는 PR은 이슈 번호만 연결하고 `Closes`를 쓰지 않는다. 병합 후 직접 닫아도 된다.

Issue·PR 본문 양식은 `docs/templates/`에서 복사해 사용한다. Markdown을 docs로 모으면서 GitHub 자동 인식 경로의 양식도 이동했으므로 자동 적용되지 않는다.

## 연동 계약·결정

- 연동 전 요청·응답·오류·검증 경계를 합의하고 계약 변경 시 관련 문서와 코드를 함께 갱신한다.
- 작은 결정은 [DECISIONS](DECISIONS.md), 중요한 선택은 ADR에 기록한다. 승인 근거와 대체 관계를 남기며 미정·후보를 승인으로 간주하지 않는다.

## 검증·기록

- 검증 결과는 [worklog 양식](worklogs/TEMPLATE.md)에 따라 같은 날짜 파일에 작업 ID별로 추가하고 TASKS·PR에서 해당 절을 연결한다.
- 검증 방법·트러블슈팅·변경 이력의 작성 위치는 [AGENTS](../AGENTS.md#작업-목적에-따라-읽을-문서)를 따른다.
